Self-host setup guide

Your life dashboard.
Your own server.

Start local, then connect your devices when you're ready. This checklist explains the setup; it does not install anything or check your server automatically.

1. Choose what you need

Just this device? Lifedash works without a sync account. Your data stays in this browser. Use Settings > Data & backups to download a portable backup regularly, especially before clearing browser storage.

More than one device? Run the app and sync server on your own host. You need a copy of the Lifedash repository, Docker Engine with the Compose plugin, writable persistent storage, and HTTPS for access beyond localhost.

This is an early-development app. Keep backups and test your setup before relying on it for important data. Container and real-device validation may still be needed for your host.

2. Start and check the stack

In a terminal at the repository root (the folder containing docker-compose.yml), run make setup for guided checks and an explicit prompt before building or starting services. It requires Python 3 and make. Use make setup-check for a read-only preflight. To run the steps directly:

docker compose version
docker compose config
docker compose up -d --build
docker compose ps
curl http://localhost:8787/api/health

The health response should be {"ok":true}. Open http://localhost:8080 on that same computer. The app uses port 8080; the sync API uses port 8787. Those are two different URLs.

The Compose port mappings listen on your host's network interfaces. Keep access restricted during setup. Anyone who reaches a fresh, empty sync server can create its first account.

If a port is already used, change only the host side of its Compose mapping, for example 8081:80. Keep the container ports unchanged.

3. Connect your first device

  1. Open Lifedash, then Settings → Sync.
  2. Enter the sync server URL: http://localhost:8787 only when the browser and server are on the same computer.
  3. Choose a username and a password of at least 8 characters, then Create account. There is no default login or email password-reset flow.
  4. Use Sync now and check the result. The root Compose setup closes registration after the first account. The sync-only Compose file in server/ explicitly leaves it open until you change its setting.

Before connecting a phone or another computer

Put the app and API behind HTTPS, using a reverse proxy such as Caddy. On the other device, localhost means that device, not your server. Use the host's reachable HTTPS app URL, then enter its reachable HTTPS sync URL in Settings.

Sign in with the same account; do not create a separate one on each device. A browser may block an HTTPS app from calling an HTTP sync API. HTTPS also enables the service worker away from localhost.

Keep the server private until setup is complete. Passwords and bearer tokens must not travel over plain HTTP outside localhost. Tokens do not expire in v1; Disconnect tries to revoke this device's token.

What sync does, and what stays local

Tasks (including their tags), projects, habits and habit logs, goals, notes, journal and focus-session history sync. Attachment metadata syncs too, and the file itself uploads to your server; another device fetches it from there when you download it. Appearance and reminder preferences sync as per-device records keyed by device id; custom wallpaper images stay on the device.

Changes sync on focus, reconnect, periodically and after edits. Simultaneous edits can conflict; the server's version wins. Sync is not a versioned backup.

4. Protect your data before upgrading

Keep a portable device backup and a server backup outside this browser and server. Settings > Data & backups creates portable v3 JSON with attachment files, focus history and automation, and checks its contents in a temporary database before requesting a download. Confirm the file was saved, then use Check an existing portable backup to check that file. Legacy Export JSON is v2: it includes focus history and attachment metadata, but no file contents. The server backup contains synced records and sign-ins - including attachment metadata and focus history, which sync. Attachment files live in the blob directory next to the SQLite file, and recent writes can live in the database's -wal sidecar, so a complete server backup needs the whole data directory or both parts below - never lifedash.db alone.

Recovery-grade, from the repository root (brief downtime; clients retry on their own):

docker compose stop sync
docker compose cp sync:/data ./lifedash-server-backup
docker compose start sync

Online (no downtime, one bounded risk): archive the blob directory, then take an online database backup with SQLite's online API. An attachment uploaded between the two steps can end up in the pair without its file, and nothing on a restored server repairs that automatically - the file only comes back from a device that still has it. Before upgrades, use the stopped snapshot above.

docker compose exec sync python -c "import shutil; shutil.make_archive('/data/blobs-backup', 'gztar', '/data', 'blobs')"
docker compose cp sync:/data/blobs-backup.tar.gz ./lifedash-blobs.tar.gz
docker compose exec sync python -c "import sqlite3; src=sqlite3.connect('/data/lifedash.db'); dst=sqlite3.connect('/data/backup.db'); src.backup(dst); dst.close(); src.close()"
docker compose cp sync:/data/backup.db ./lifedash-backup.db

Rename or archive the copied file before the next backup, which overwrites it. Treat it as private: it contains account data and bearer tokens. Do not copy a live database file alone while SQLite is writing to it.

Known hazard: restoring an older backup can silently corrupt multi-device sync. Devices assume the server's change counter only moves forward; a restore moves it backward and reuses numbers, with no detection today - a device can miss post-restore changes, and conflict handling can keep the server's older version over a newer edit. Until a designed reconciliation ships, there is no verified repair procedure. The cautious manual path after restoring an older backup: hold off editing, compare every device's data against the server, and re-enter anything missing by hand. Treat that as careful review, not a proven repair. Reconnecting devices does not repair the restore.

docker compose down keeps the volume. Do not add -v: that deletes the data volume. Before upgrading, keep the current code version and backup. Restore into a separate test instance first; replacing a live database is destructive. Full recovery steps are in server/SELFHOST.md in your checkout.

When something doesn't work

The app opens, but Sync can't reach the server

Check the API URL, not the app URL. Visit /api/health on that API host from the same device. Check your firewall, HTTPS certificate and reverse proxy. A working app page does not prove the API is reachable.

docker compose ps
docker compose logs --tail=100 sync

Do not share logs containing personal data or credentials.

Registration is closed, or sign-in fails

A 403 during account creation is expected after the first account in the root setup. Use Sign in for an existing account. A 401 means the credentials did not match. To deliberately add an account, temporarily set SYNC_OPEN_REGISTRATION: "1" on the sync service, recreate it, then close registration and recreate it again.

A task synced, but its attachment didn't

Attachment metadata syncs and the file uploads to the server; the second device gets it when you choose Download on the attachment. If the upload has not finished or the server refused it, the source device shows the file as on this device only, with a Retry for refused uploads. Settings > Data & backups makes a portable backup with file contents. Legacy Export JSON has metadata only, and the server SQLite backup does not contain the files themselves - they live in the blob directory next to it.

I only want to test the backend locally

After make install, run make test-selfhost on a POSIX host. It starts temporary loopback servers and synthetic databases, checks restart persistence and online backup/restore, then removes them. It does not validate Docker, TLS or a real device.

This guide is bundled with Lifedash. It does not contact an external service, collect credentials or change your server. For reverse-proxy and bare-metal examples, see server/SELFHOST.md.
